Concept v1 · 2026-08-11 · not built

The public web surface.
Built for Google, not for climbing.

A read-only server-rendered site on the same Supabase. Its only job is to rank for climbing searches and hand the visitor to the app. The gated asset is the line, not the name. Names, grades and counts are indexable text. Which line on the rock is which problem stays behind sign-up.

Public & indexed by Google
Gated — account required
Changed in v1

v0 gated the problem list. It is now public: name, grade, and count are all crawlable. The gate moved onto the line overlay, which is the correct place because the line drawing is the thing your users actually contributed and the thing a competitor would want to copy. This makes the SEO case substantially stronger, because problem names are the long-tail search text.

03

The boulder page, and the one decision left

This is where the gate physically sits. The photo is public, the problem list is public, the line overlay is not. The open question is whether guests see the lines anonymously or not at all.

A  Clean photo
recommended
ラインはアプリで
このボルダーには7本のラインがあります。無料アカウントで表示。
No line paths rendered at all. The photo shows the rock, the list below names all 7 problems and grades, and the overlay states how many lines exist without drawing any of them. Zero leak by construction.
costA guest cannot judge whether the line quality is good, so the sign-up is slightly more of a leap of faith.
B  Anonymous lines
alternative
どのラインがどの課題か
名前とグレードの対応はアプリで
Lines drawn in neutral gray, dashed, with no labels or numbers. The guest sees that the line work is dense and well drawn, which is a stronger pitch, but cannot tell which line is 忍者返し.
the flawDeduction by elimination. On a boulder with 1 or 2 problems the mapping is trivially obvious, and on any boulder a determined person can guess from grade order. The leak is small but it is real, and it scales with how many one-problem boulders you have.

My recommendation is A. B leaks by elimination on exactly the small boulders where a single line is the whole value, and the extra persuasion it buys is not worth writing a rule like "only show anonymous lines when the boulder has 4 or more problems". If you want B's persuasive effect without the leak, the safer version is a count plus a thumbnail of the line overlay from a different boulder used as a marketing image, which is what the app-store screenshots already do.

06

How it's actually built

No Expo Web, no app parity, no second auth system, no writes.

Google / 検索
  ↓
Next.js on Cloudflare or Vercel  — server-rendered, read-only, no client Supabase key
  ↓  service-role read, server side only
get_crag_public(slug) / get_problem_public(slug)
  returns: name, grade, boulder, crag, access, parking, counts
  never selects: line geometry, hold coords, beta, comments, ascent rows
  ↓
Supabase  — same database the app uses, zero schema forks

The app is untouched. The gate is one column list in one SQL function.
Why the whitelist matters
The public field list lives in one place instead of scattered across page templates. If the geometry column is not in get_problem_public, it cannot leak no matter what a future page renders.
Rough size
Two RPCs, a crag route, a problem route, a prefecture index, a sitemap generator, and the JSON-LD. Days, not months, because there is no auth, no state, and no writes.
